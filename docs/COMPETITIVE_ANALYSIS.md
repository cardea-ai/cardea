# Cardea 경쟁 솔루션 분석

변경 이력은 `docs/history/COMPETITIVE_ANALYSIS.md`에서 관리한다.

`docs/requirements.md`, `docs/EDITIONS.md`를 기준으로 현재 AI 게이트웨이·DLP 시장과 비교한
경쟁력 평가와 Build vs Buy 판단이다. 웹 검색(2026년 기준 공개 자료)으로 확인한 경쟁사
정보이며, 가격·인증·성능 수치는 각 업체의 공개 주장을 그대로 인용한 것으로 직접 검증하지
않았다.

## 1. 경쟁 지형

## 2. 명세 대비 평가

### 이미 잘 방어된 부분

- GW 챕터(라우팅·어댑터·관측)는 자체 구현이 아니라 Bifrost core를 임베드하는 결정
  (ADR-0001)을 이미 내려서, LiteLLM/Portkey와 제로부터 경쟁하지 않고 "조립"으로 가는
  선택을 했다. 이 영역은 추가 자체 개발 리소스가 필요 없다.
- 오픈코어 PLG(무료 개인용 로컬 에이전트 → 조직 전환) 전략은 검색된 국내 경쟁사(GenAI
  Shield, Corepin, Airgap Studio) 중 누구도 쓰지 않는다. 전부 B2B SaaS/API 판매 모델다.
  개발자가 먼저 무료로 쓰다가 회사가 따라오는 구조는 실제 차별점이다.
- 에이전트/MCP 거버넌스(AG-01~12, 특히 메모리 거버넌스 AG-06·세션 오염 추적 AG-04)는
  국내 경쟁사 어디에도 없다. 국내 업체들은 "텍스트 PII 탐지+게이트웨이"에 머물러 있고,
  "에이전트가 메모리·스킬에 오염된 정보를 쌓는 문제"는 다루지 않는다.

### 위험한 부분 (명세가 과대평가한 차별점)

- "한국 민감정보 탐지"는 더 이상 공백 시장이 아니다. Corepin은 탐지율 99.99%·오탐 0건을
  주장하며 외산 대비 1/30 가격, Airgap Studio는 100ms 이내·오프라인 동작, 엘세븐시큐리티는
  GS 1등급 인증까지 받고 조달청에 등록돼 있다. **순수 탐지 정확도·속도 경쟁으로는 이미
  늦었다.** NFR-DQ(평가셋 기준선)를 돌렸을 때 이들과 동등 이하라면, Cardea만의 이유가
  사라진다.
- GW-01~09를 "직접 만든다"는 인상을 주는 서술(FR-GW 신설 챕터, 당근 사례 근거)이 과하다.
  실제로는 Bifrost를 쓰므로 괜찮지만, 문서상으로는 "LiteLLM/Portkey를 다시 만드는
  프로젝트"처럼 읽혀서 팀 내부에서도 스코프 오해가 생길 수 있다.
- 당근 사례가 보여준 건 "사내 전용, 자금과 전담 ML 인프라 조직이 있는 회사가 1~2년
  투자해서 만든 결과"다. 같은 걸 외부 판매용 제품으로 다시 하려면 비용 구조가 완전히
  다르다.

## 3. Build vs Buy 판단

목적에 따라 결론이 갈린다.

### 목적이 "우리 회사가 섀도 AI·유출을 막는 것"(내부 도입용) → Buy/조합을 추천

- LiteLLM(또는 이미 쓰기로 한 Bifrost) + Airgap Studio Data Guard나 Corepin API를 DLP
  플러그인으로 붙이는 조합이면 수개월 내 전사 적용이 가능하다.
- Cardea 명세 전체(FR 60여 개 + AG 12개 + GW 9개 + NFR 다수)를 자체 구현해서 같은 수준에
  도달하려면 최소 1~2년, 전담 보안+인프라 팀이 필요하다. 내부용으로는 ROI가 안 맞는다.

### 목적이 "이 명세로 제품을 만들어 판매"(사업화) → 조건부 Build를 추천

조건은 두 가지다.

1. **스코프를 좁힌다.** GW 챕터는 Bifrost 조립으로 계속 가고(이미 맞게 결정됨), 직접
   개발 리소스는 국내 경쟁사 누구도 안 하는 조합 — **모델 비도달 보장(코어 보안 원칙)
   + 에이전트·MCP 거버넌스 + 오픈코어 PLG** — 세 가지의 교집합에 집중한다. 한국 규제
   (N2SF/ISMS-P/폐쇄망) 대응은 그 아래 "로케일별 선택 모듈"로 두고 전략의 중심축으로
   쓰지 않는다 — 지역에 묶이면 해외 확장과 오픈소스 커뮤니티 유입에 불리하다.
2. **탐지 정확도를 사업의 근거로 쓰지 않는다.** Corepin·Airgap Studio와 같은 조건으로
   NFR-DQ 평가셋을 돌려 "최소 동등"임을 먼저 확인하고(안 그러면 가격·정확도 싸움에서 질
   수 있음), 그 위에 "이들에게는 없는 에이전트 거버넌스·조직 정책·오픈코어 유통"을 얹는
   구조로 포지셔닝한다.

## 3-1. OSS 적극 채택 재검토

"필요한 기능 중 이미 안정적인 오픈소스가 있으면 그걸 쓴다"를 원칙으로 FR/AG/NFR
전 영역을 다시 훑었다. 결론: 위 4장의 "전부 자체 개발, 최소 1~2년"이라는 비관적
추정은 **탐지 엔진·가드레일 아키텍처·시크릿 스캐너·서명/SBOM·토큰 금고 크립토
백엔드까지 성숙한 OSS로 조립 가능하다는 걸 반영하면 과대평가**였다. 자체 개발 범위는
"이 조합을 보안 게이트웨이로 묶는 접합부"로 좁아진다.

| 영역 | 적용 가능 OSS | 라이선스/성숙도 | Cardea에서 하는 일 |
|---|---|---|---|
| FR-PI 탐지 엔진 | Microsoft Presidio (`AnalyzerEngine`/`AnonymizerEngine`) | MIT, 커뮤니티 거버넌스(Data Privacy Stack)로 이전 중, 다년 운영 사례 多 | 자체 NER/정규식 엔진을 처음부터 안 만든다. Presidio는 이미 한국(Korea) 전용 recognizer를 포함하므로, 한국 민감정보 신규 엔티티(주민번호 체크섬, 우회 표기 정규화 FR-PI-11 등)는 Presidio의 custom recognizer/컨텍스트 단어로 플러그인화해 얹는다. ADR-0002의 "탐지기" 슬롯 구현체로 Presidio를 감싼다 |
| 가드레일 아키텍처 참고 | NVIDIA NeMo Guardrails | Apache 2.0, NVIDIA 유지보수, Limina가 실제 플러그인으로 채택한 선례 있음 | 그대로 임베드하지는 않지만(코어는 Go, 플러그인 런타임은 ADR-0002 4종), input/retrieval/dialog/execution/output 5-rail 모델을 Cardea의 6-슬롯(정규화기→탐지기→분류기→정책→처리기→연동) 설계와 교차검증하는 참고 아키텍처로 쓴다. 특히 execution rail(툴 호출 입출력 검증) 개념은 AG(툴 통제) 슬롯 설계에 직접 반영한다 |
| NFR-SS-05 자가 탐지(운영 로그 시크릿 검사) | gitleaks | Go, MIT, 2.7만+ stars, 단일 바이너리 | CI와 런타임 로그 스캐닝에 바이너리를 그대로 호출한다. 자체 시크릿 탐지 재구현을 하지 않는다. 로그가 큰 경우 trufflehog(활성 자격증명 검증)을 보조로 고려 |
| NFR-SC-01~03 서명/SBOM | cosign(sigstore) + syft/grype(Anchore) | 모두 Apache 2.0, CNCF/업계 표준 | 이미 방향은 맞았다(명세에 "cosign 서명, SBOM 동반"으로 적혀 있음) — 이번엔 도구명을 명시적으로 박아, "직접 서명 체계를 만든다"는 오해를 차단한다 |
| FR-PI-04/FR-TK-05 토큰 금고의 암호화 백엔드 | OpenBao (HashiCorp Vault의 BSL 전환 이전 코드 포크) | MPL 2.0, Linux Foundation/OpenSSF 샌드박스 프로젝트, Vault와 API 호환 | Transit 엔진(암호화as서비스, envelope encryption, 키 로테이션)과 Transform 엔진(토큰화·형태보존암호화)을 토큰 금고의 크립토 계층으로 쓴다. Cardea가 직접 구현하는 부분은 "원문↔토큰 매핑, 세션/요청 스코프 만료, FR-PI-04가 요구하는 비결정론적 토큰 발급 정책"뿐이다. **주의**: HashiCorp Vault 자체(1.15+)는 BSL 1.1이라 CLAUDE.md의 Apache-2.0 오픈코어 공약과 맞지 않으므로 Vault가 아니라 OpenBao를 채택 대상으로 명시한다 |
| MCP 게이트웨이 1차 계층(AG-02/03 기본 인증·allowlist) | Bifrost core (이미 ADR-0001로 임베드 결정됨) | Apache-2.0, 이미 코어에 있음 | Bifrost가 이미 virtual key 단위 MCP 툴 allowlist + OAuth 2.1(DCR/PKCE) 인증을 제공한다. 이 기본 인증/허용목록 계층을 Cardea가 다시 만들지 않고 Bifrost 설정으로 해결한다. Cardea가 추가하는 것은 Bifrost가 안 하는 "툴 호출 인자의 콘텐츠 검사(프롬프트 인젝션·PII·시크릿 패턴, AG-02/03의 핵심)"뿐이다 — 이 지점은 Lasso Security의 오픈소스 MCP 게이트웨이(콘텐츠 검사 중심)를 설계 참고로만 쓴다(의존성으로 채택하지 않음) |

**채택하지 않는 것**: FR-PI-04 토큰 금고 자체를 위해 검색된 소규모 OSS
(`openpii-vault`, `clawwarden`, npm `pii-vault` 등)는 스타 수·유지보수 이력·보안
감사 기록이 불명확해 **채택하지 않는다.** 금고처럼 보안 critical한 컴포넌트를
검증 안 된 소규모 프로젝트에 의존시키면 CLAUDE.md의 서명·SBOM·공급망 기본값과
상충한다. 매핑 테이블·만료·스코프 로직은 Cardea 자체 구현 + OpenBao라는 성숙한
크립토 백엔드의 조합으로 간다.

이 조합을 적용하면 자체 개발 범위는 "탐지 엔진 자체를 만드는 것"에서 "① 로케일별
정규화·엔티티 플러그인(한국 민감정보 유형 포함), ② 가역 마스킹의 세션 스코프·매핑
로직, ③ 사람 채팅+에이전트 툴 호출을 하나로 묶는 정책 오케스트레이션 레이어"로
좁혀진다. 아래 4장의 결론 중 "전부 자체 개발은 최소 1~2년"이라는 수치는 이 OSS 조합을
전제로 하향 조정해야 한다.

## 4. 결론

지금 명세 그대로 "전부 자체 개발"은 범위가 너무 넓어 보였지만, OSS 적극 채택(3-1장)을
반영하면 그 절반은 조립(Bifrost core + Presidio + OpenBao + gitleaks/cosign/syft)으로
풀리고, 자체 개발은 "로케일별 탐지 플러그인(한국 민감정보 유형 포함) + 가역 마스킹
세션 스코프 로직 + 사람 채팅/
에이전트 툴 호출 통합 정책 엔진"으로 좁혀진다. 순수 사내 도입이면 사지 말고 조합해서
쓰는 게 합리적이고, 사업화가 목적이면 "민감정보가 모델에 도달하지 않는다는 보편적
보안 원칙 + 에이전트 거버넌스 + 오픈코어"라는 좁은 쐐기에 걸고 Build하되, PII 탐지
자체도 한국 규제 대응도 핵심 세일즈 포인트로 쓰지 않는 쪽으로 명세를 다시 다듬어야
한다. 다만 자체 개발로 남는 범위가 OSS 조립 전 추정보다 훨씬 작아졌으므로, "최소 1~2년,
전담 팀 필요"라는 기존 추정은 재검토 대상이다(정확한 재추정은 작업 2의 Getting Started
설계 때 모듈별로 다시 가늠한다).

| Skyflow (Data Privacy Vault / Skyflow for Agents) | 폴리모픽 암호화+토큰화, MCP 데이터 보호 레이어, 에이전트 아이덴티티 바인딩, 정책 기반 rehydration. **"context graphs, memory stores, prompts에서 PII를 뺀다"고 명시** | SaaS 볼트(리전별 배치 가능), 전용 볼트 격리 | FR-PI-04(가역 마스킹)+AG-06(메모리 거버넌스)과 거의 동일한 메시지를 이미 공개적으로 쓰고 있음. "메모리에 PII를 안 남긴다"는 Cardea만의 차별 사례가 아니다 |
| Protecto | CBAC(Context-Based Access Control) — 역할만이 아니라 "누가, 어떤 작업으로, 어떤 컨텍스트에서" 요청했는지를 **추론 시점에 동적으로** 판단해 재식별 범위를 결정. 같은 데이터에 같은 역할이어도 작업(task)에 따라 다른 뷰. | Limina (구 Private AI, 2026-03 리브랜딩) | 50+ 엔티티·52개 언어 탐지, 리댁션/가명화/합성데이터/가역 토큰화. **게이트웨이가 아니라 "빌드블록"** — 토큰 저장소·복원 로직은 고객이 직접 연결해야 함(토큰 스토어 자체 구축 필요) | 컨테이너를 고객 VPC/온프렘에 배치, SaaS도 있음 | FR-PI-01~03(탐지)과는 겹치지만, MCP·에이전트·메모리 거버넌스는 제품 범위 밖. 단일 게이트웨이로 묶는 Cardea의 구조적 차별점은 유지됨 |
| Nightfall AI (MCP Gateway, 2026-09 출시) | MCP 서버 가시성(발견·리스크 평가)+MCP Gateway(자격증명 브로커링, 툴 단위 허용/차단)+Claude Inference Hooks(사람 채팅 콘텐츠 검사)로 **4개 분리된 표면**을 운영. 공식 문서: "MCP Gateway는 프롬프트 텍스트를 스캔하지 않는다. 툴 인자 콘텐츠 스캔은 이번 릴리스에 없다" | SaaS, 엔드포인트 에이전트 설치 필요 | AG-02/03(MCP 게이트웨이)과 겹치지만 **콘텐츠 검사와 툴 거버넌스가 분리돼 있다는 게 명시된 약점.** Cardea가 "사람 채팅 + 에이전트 툴 호출을 하나의 정책 엔진으로" 묶는다는 주장(POSITIONING.md 한 줄 포지셔닝)은 Nightfall과 비교하면 구체적인 비교 우위로 남는다 |

Cardea의 "오픈코어·클라우드 비의존·폐쇄망" 차별점은 NoPII에는 그대로 안 맞고 유지된다 |

### 재검증 결론

1. **"메모리에 PII를 안 남긴다"는 차별점은 더 이상 유효하지 않다.** Skyflow가 이미
   "context graphs, memory stores에서 PII를 뺀다"를 공개 메시지로 쓰고 있다.
   `docs/POSITIONING.md`의 "증거를 쌓는 순서" 2번(에이전트 메모리 노출 차단 데모가
   차별화 증거)은 더 좁혀야 한다 — Skyflow와 똑같은 데모를 만들면 "이미 있는 걸 또
   만들었다"로 보인다.
2. **FR-AC-03(break-glass)은 Protecto의 CBAC보다 뒤처진 설계다.** 단순 "승인 거쳐
   예외 허용" 모델이 아니라 "역할+작업(task)+컨텍스트를 매 요청마다 평가해 재식별
   범위를 동적으로 결정"하는 쪽으로 설계를 올려야 한다. 이건 사업화 이전에 명세
   보완이 필요한 실질적 격차다.
3. **"모델 비도달 보장" 원칙 자체는 여전히 구조적으로 유효하지만, 더 좁은 쐐기가
   필요하다.** 좁혀야 할 지점은 다음 세 가지의 교집합이다.
   - (a) **오픈코어·로컬 우선·클라우드 비의존**: Skyflow·Protecto·Nightfall은 모두
     SaaS/호스팅 볼트가 기본이고, NoPII는 클라우드 프록시 전용이다. 다섯 곳 중
     "자체 호스팅 바이너리를 무료로 영구 쓸 수 있는" 곳은 없다. 이 축은 그대로
     유지된다.
   - (b) **사람 채팅과 에이전트 툴 호출을 한 정책 엔진으로 묶는다**: Nightfall은
     이 둘을 4개 분리된 표면(Inference Hooks/IDE hooks/Compliance API/MCP Gateway)으로
     나눠 운영하고, 공식 문서에서 "MCP Gateway는 콘텐츠를 안 본다"고 명시한다.
     Skyflow·Protecto는 에이전트/MCP 중심이고 사람의 일반 채팅 게이트웨이 역할은
     약하다. 이 결합은 Cardea가 비교 우위를 주장할 수 있는 구체적 지점이다.
   - (c) **CBAC 수준의 동적 재식별(FR-AC-03 보완 필요)**: 지금 명세로는 이 지점에서
     Protecto에 뒤처진다. 보완 전까지는 "break-glass"를 차별점으로 내세우지 않는다.
4. **NoPII·Nightfall과는 "오픈코어/클라우드 비의존"으로, Skyflow·Protecto와는
   "통합 정책 엔진(사람+에이전트)"으로, 전체적으로는 아직 "CBAC 격차 해소"가 선행
   조건으로 다르게 싸워야 한다.** 다섯 경쟁사를 하나의 메시지로 뭉개서 비교하면
   안 된다.

## 6. 후속 조치 제안 (미결 사항)

- `docs/requirements.md` 8장에 ADR-0007(신설 제안)을 추가해 Presidio·OpenBao·gitleaks·
  cosign/syft·Bifrost 기존 MCP allowlist 조합을 공식 결정으로 못박는다. 사용자 승인 후
  "제안"을 "확정"으로 바꾼다.
- Presidio를 탐지기 슬롯 백엔드로 채택할 때 성능 영향(Python 기반, gRPC 분리 프로세스로
  호출 — 7장 기술스택의 "ML 분류기는 Python, gRPC, 프로세스 분리" 원칙과 일치하는지)과
  Rust/TinyGo WASM 정규화기 플러그인과의 경계를 설계 문서로 구체화한다.
- OpenBao의 Transform 엔진(토큰화·형태보존암호화)이 FR-PI-04의 "결정론적 해시 금지, 난수
  토큰만 허용" 요건과 호환되는지 — Transform 엔진의 FPE(형태보존암호화) 모드가 아니라
  난수 기반 토큰 생성 모드를 쓰도록 설정 가이드를 먼저 검증한다.
- NFR-DQ-02 한국어 평가셋으로 Corepin/Airgap Studio와 동등한 조건의 벤치마크를 돌려
  Cardea 탐지 엔진의 실제 위치를 확인한다 (사업화 전 선행 조건). **1차 스파이크 완료
  (2026-10-25)**: `eval/nfr-dq/`에서 체크섬 식별번호(KR_RRN·KR_CARD_NUMBER·
  KR_BIZ_REG_NO) 탐지를 합성 평가셋 46건으로 검증 — 재현율 1.0000, 정밀도 0.9714로
  NFR-DQ-01 목표(99%/95%)를 충족했다. 과정에서 Amex 카드 패턴 누락 버그를 고쳤고,
  체크섬 단독 탐지가 운송장 번호 같은 비(非)PII 13자리 숫자에 거짓양성을 낸다는
  구조적 한계를 실측으로 확인했다 — 문맥 단어 가중치(Presidio
  ContextAwareEnhancer 패턴)를 Go 구현의 필수 요건으로 추가해야 한다. **단, 경쟁사
  제품을 직접 실행해 비교한 게 아니라 Cardea 설계 자체의 목표 충족 여부만 확인한
  것이라, "동등 조건 비교"는 여전히 미해결 과제다**(`eval/nfr-dq/README.md` 참고).
  이름·주소 등 체크섬 없는 엔티티의 NLP 기반 탐지는 이번 스파이크 범위 밖이다.
- 명세 1장 "제품 정의"에 "PII 탐지 정확도와 한국 규제 대응은 핵심 차별점이 아니다"를
  명시하고, 차별점을 모델 비도달 보장(코어 보안 원칙)·에이전트 거버넌스·오픈코어 유통
  묶음으로 재정의하는 문구를 반영했다(`docs/POSITIONING.md`, `docs/requirements.md`
  1장 보완 참고).
- GW 챕터 설명에서 "직접 만든다"는 인상을 주는 서술을 "Bifrost 조립 + 얇은 어댑터 계층"
  으로 더 명확히 교정할지 검토 (내부 스코프 오해 방지).
- FR-AC-03(break-glass) 수용 기준을 Protecto의 CBAC와 같은 틀 — 역할(role) 고정이 아니라
  역할+작업(task)+컨텍스트를 매 요청마다 평가하는 동적 재식별 — 로 다시 쓴다. 승인 절차
  (break-glass)는 "CBAC가 거부한 경우의 예외 경로"로 하위에 두고, 1차 결정 로직 자체를
  정적 RBAC에서 CBAC급으로 올린다.
- `docs/POSITIONING.md` "증거를 쌓는 순서" 2번(에이전트 메모리 노출 차단 데모)을 Skyflow와
  차별화되는 형태로 다시 설계한다 — 단순 "메모리에 PII 안 남음" 데모가 아니라 "오픈소스
  자체 호스팅 상태에서 사람 채팅과 에이전트 툴 호출을 하나의 정책 엔진으로 통제"하는
  데모로 좁힌다(5장 재검증 결론 3-(b) 참고).
